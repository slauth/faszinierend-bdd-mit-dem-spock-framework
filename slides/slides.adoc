== Was ist das Spock Framework?

[quote,https://spockframework.org/]
Spock is a *testing*, *specification*, and *mocking* framework for JVM developers that emphasizes *readability* and *clarity*.

== Wozu überhaupt?

[%step]
Für Tests haben wir doch *JUnit*.

=== Der perfekte Test

[%step]
Ein guter Test zeigt auf einen Blick zwei Dinge:

[%step]
. was die Anwendung machen _soll_ +
   (→ *Spezifikation*)

. ob sie dies _tatsächlich_ macht +
   (→ *Verifikation*)

[.notes]
--
* JUnit: Fokus auf *2.*
* Trend zum *Spec Driven Development* (mit Markdown)
* Spock (im Gegensatz zu Markdown) = *ausführbare* Specs
--

[.notes]
--
* Szenario: Service erzeugt selbst ein Objekt (mit generierter Bestellnummer) und übergibt es an einen Mock
* `equals` reicht nicht → übergebenes Argument „einfangen“ und dann prüfen
--

=== JUnit

[source,java,indent=0]
----

[.notes]
--
* `ArgumentCaptor` muss vorab deklariert werden – inkl. Generics-Boilerplate
* `capture()` versteckt sich *innerhalb* von `verify()`
* Danach `getValue()` holen und Feld für Feld mit AssertJ prüfen
* Drei Schritte (deklarieren → einfangen → auspacken) für eine Prüfung

== Fehlermeldungen

=== JUnit

----
org.opentest4j.AssertionFailedError: expected: <0> but was: <1>
----

=== Spock

----
Condition not satisfied:

calculator.discountFor(customer, order) == expected
|          |           |         |      |  |
|          0.00        |         |      |  5.00
|                      |         |      false
|                      |         Order[total=100.00]
|                      Customer[memberSince=2026-10-05]
<de.slauth.spock.discount.DiscountCalculator@6401d0a0>
----

[.notes]
--
* Power Assertions: ein einfaches `==` zeigt jeden Zwischenwert
* Kein Debugger, kein AssertJ/Hamcrest-DSL nötig

== Einstieg ohne Big Bang

* Spock läuft auf der JUnit-Platform
    ** gleicher Maven-/Gradle-Build
    ** gleiche IDE
    ** gleiche CI
* Produktionscode bleibt Java
* Spock-Specs und JUnit-Tests leben friedlich nebeneinander 🖖

* Antwort auf „Muss ich alles auf einmal umstellen?“ – nein
* Vorschlag: nächsten neuen Test als Spec schreiben

== 3 Dinge zum Mitnehmen

[%step]
. *Lesbar:* Given-When-Then als echte Struktur – Specs, die sowohl das Business als auch dein KI-Agent versteht
. *Datengetrieben:* `where:`-Tabellen statt `@MethodSource`
. *Aussagekräftig:* Power Assertions erklären jeden Fehlschlag

[.notes]
--
* Und der Einstieg kostet fast nichts – einfach ausprobieren 🖖
